## 真实认证在哪里

主机上的可信控制器读取现有 `/Users/junyuc/.codex/auth.json`，不修改它。
控制器只通过 Docker exec 的匿名标准输入管道，将访问令牌和账户选择标识传给独立可信代理。
不通过 argv、环境变量、镜像、挂载或临时凭据文件传递；代理进程只在内存中持有它们。
refresh token 和真实 ID token 留在可信主机，不进入代理，更不进入候选容器。

候选容器的 auth.json 只包含随机临时 nonce、合成账户标识和不可刷新占位符。
这份文件使原生 CLI 保持 ChatGPT 模式。它不是用户账户的认证文件。
代理仅监听候选专用内网 IP；仅代理有第二张联网网卡，候选没有公网路由。
代理用真实账户头向固定的 `https://chatgpt.com/backend-api/codex/` 发请求。
TLS 验证开启，不跟随重定向，不使用调用者指定的目的地址或环境代理设置。

候选能读取并使用临时 nonce，因此可以在许可时间与配额内消耗账户推理资源。
这项设计保护长期账户凭据，不能让不可信代码无法使用它本来就被授权使用的会话能力。

## 隔离和边界检查

实际 Docker inspect 确认：无主机绑定挂载、无共享 PID 命名空间、无发布端口、非特权容器、
UID 1000、只读根文件系统、cap-drop ALL、no-new-privileges、core dump 禁用。
每容器 2 CPU、4 GiB 内存、128 PID；候选可写目录均为限额 tmpfs。

实际候选文件系统记录了 12,291 个文件条目及 SHA-256/符号链接信息，排除了 proc/sys/dev
这些动态伪文件系统。没有 `/base`、主机认证路径、Docker socket 或 pytest_5786 材料。
这是全新最小合成镜像，不复用含任务说明的 Pilot `/base` 目录。

模型调用前后，可信主机接收候选全部可写目录及可读进程环境的扫描流，直接比对真实令牌。
扫描程序本身不接收真实令牌。只保存文件哈希；原始扫描流不落盘。
CLI 输出也在写入证据前做同样检查。只读镜像、独立挂载/PID 空间与上述检查共同支持隔离结论；
不声称这是针对所有内核漏洞或旁路的形式化安全证明。

代理限制：仅模型目录 GET 和固定模型 Responses POST；一次上游目录读取并缓存；
最多 12 次 Responses 尝试（失败不退配额）；单并发；会话 300 秒；Agent 240 秒；
请求体最多 2 MiB、响应最多 16 MiB。响应先缓冲、检查，再向候选返回。
重复认证/长度头、编码/分块请求、错误模型、任意路径、后台请求和历史 response ID 被拒绝。
上游错误和重定向不原样返回；发现访问令牌则拒绝；非秘密账户标识若出现则替换为合成值。

单元测试覆盖 nonce、过期、撤销、配额、并发占用、目录缓存、畸形请求、超限、重定向、
上游错误、凭据回显、账户标识替换、TLS/头部白名单，以及 SSE 的 Content-Type 兼容性。
真实环境另验证了网络阻断、文件/PID 边界、原生工具和代理销毁后的撤销效果。

## 调试过程完整保留

没有将失败记录覆盖为成功，也没有把它们算作模型能力失败。
每次 CLI 会话的请求/流自动重试均为零。实现修正后人工发起了不同的新诊断会话；
因此不能说整个调试过程“只运行过一次模型”。

1. `live-preflight-01`：隔离检查把自身命令中的代理名称误判成代理进程；未读真实认证。
   改为比较完整 argv 项，后续离线预检通过。
2. `live-account-01`：目录启动竞争，CLI 提前收到 429/403；上游推理请求为零。
   先完成一次目录验证并缓存，避免原生 CLI 重复发现请求与单次目录配额冲突。
   单独的 `catalog-01` 使用真实账户取得目录 200，未调用模型。
3. `live-account-02`、`03`：各一次推理请求，上游均 200，代理返回 502。
   诊断确认响应类型检查拒绝了结果；03 的记录排除了秘密、大小和期限问题。
   账户标识回显不是这次故障原因，该检查补强保留为防御措施。
4. `live-account-04`：确认真实服务的 Content-Type 为空，但响应具有完整 SSE 事件。
   仅对可解析完整响应做类型规范化后，原生编码成功，源码独立断言通过。
   合成镜像未包含 pytest，Agent 如实报告测试命令失败；最终控制器测试步骤失败。
5. 改用不需新依赖的 Python 标准库 unittest；离线先确认缺陷会触发预期断言。
   `live-account-05` 完成上述全部闭环和销毁撤销检查。

总计五次原生 CLI 启动，四个会话发生上游推理，共八次 Responses 请求。
这些全是合成链路诊断，B/C Trial 数始终为零。

## 能支持什么，尚未支持什么

现在已有实际证据说明：**可以保留 Codex 账户登录，让原生 Codex 执行代码，同时不把真实账户
认证交给候选容器。** 这条最小代理方案可作为 Harbor 适配的基础。

尚未把代理接进 Harbor adapter，也没有重新声明 B/C 的 runtime provenance 已通过。
下一步只需窄范围适配：由可信 Trial 生命周期管理代理，向候选发临时配置，保持原独立 verifier
和 trusted patch handoff，记录新代理身份，并重新检查实际 B/C 环境。不能把本合成检查冒充
B/C 完整泄漏审计或 A/B/C 完全同条件比较。

本次只验证当前有效的账户令牌；要求启动时剩余有效期大于 360 秒，否则拒绝启动。
不刷新令牌、不改用户登录文件。长期无人值守运行仍需在可信侧处理登录刷新与并发刷新协调，
以及服务监督、崩溃注入验证和故障清理。没有验证 WebSocket、压缩、长任务流式时延；
当前缓冲 SSE 会增加单轮响应延迟。请求数/时间限制不是严格货币预算。

本次安全边界改变后工具审批允许执行，不等于以后任意部署都自动获得授权。
原先“把主账户 auth.json 注入候选容器”的被拒方案未重试，也未被换包装执行。
